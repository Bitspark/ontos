# Proposal: a finite extensional value algebra

I would freeze the foundation as the least model that can say three things and no more:

1. **Here is uninterpreted data.**
2. **Here are values in an ordered arrangement.**
3. **Here are values associated with values, without order.**

Everything else—numbers, text, truth, time, signatures, links, schemas, facts, trust, variables, records, namespaces—belongs above the foundation.

Formally, define the universe of values as the least well-founded set `V` generated by:

```text
Value ::=
    Atom(bytes)
  | Sequence(Value*)
  | Map(finite partial function Value -> Value)
```

Where:

```text
bytes = a finite sequence of octets
Value* = a finite ordered sequence of values
Map = a finite set of key/value pairs with no duplicate keys by value identity
```

Equivalently:

```text
V = μX . Bytes + List(X) + FiniteMap(X, X)
```

The `+` is a disjoint sum: an empty byte atom, an empty sequence, and an empty map are three different values.

That is the whole model.

A value is not a message, object, fact, assertion, location, record, encoding, schema instance, or authority-bearing statement. It is a closed, immutable, finite, context-free term in this algebra.

---

## 1. Core semantics

### 1.1 Values are finite, immutable, well-founded terms

A value is a mathematical object, not a runtime object.

It has no address, no owner, no creation time, no storage location, no identity apart from its contents, no hidden metadata, no mutable state, and no observable sharing.

Values are finite. There are no infinite lists, streams, lazily computed values, cyclic structures, promises, thunks, or references in the foundation.

A graph, stream, database row, certificate chain, AST, proof, tensor, or signed claim may all be represented as values, but the foundation does not know those concepts.

### 1.2 Atom

An atom is an opaque finite byte string.

```text
Atom(0x)
Atom(0x66 0x6f 0x6f)
Atom(0xde 0xad 0xbe 0xef)
```

The bytes have no built-in interpretation. They are not text, not integers, not compressed data, not hashes, not public keys, not MIME payloads, not booleans. Higher layers may interpret atoms that way.

The foundation only says: these exact bytes are present.

### 1.3 Sequence

A sequence is a finite ordered sequence of values.

```text
Sequence()
Sequence(Atom("a"), Atom("b"))
Sequence(Atom("x"), Map(...), Sequence(...))
```

Order is semantic. Length is semantic. Duplicate elements are allowed. The first occurrence and second occurrence of equal values are distinct positions, though the repeated subvalue itself has no object identity.

A sequence is the foundation’s only ordered composition form.

### 1.4 Map

A map is a finite partial function from values to values.

```text
Map {
  Atom("name") -> Atom("Ada"),
  Atom("age")  -> Atom(0x25)
}
```

The keys may be any values, not just atoms. Values may also be any values.

Map entry order is not semantic. A map is not a list of pairs. It has no insertion order. It has no duplicate keys. If a concrete syntax or encoding presents two entries with equal keys, that syntax has failed to denote a valid foundational map unless the encoding layer defines a rejection or normalization rule before producing the value.

The map constructor is deliberately functional, not relational, not multivalued, and not ordered. If a consumer needs a multimap, ordered map, relation, table, graph edge list, or log, it can represent that using sequences and maps above the foundation.

### 1.5 Constructors are disjoint

These are different values:

```text
Atom(0x)
Sequence()
Map {}
```

Likewise:

```text
Atom(0x01)
Sequence(Atom(0x01))
Map { Atom(0x01) -> Sequence() }
```

are all distinct.

This is not a type system in the usual sense. It is merely the minimum constructor distinction required for values to round-trip without ambiguity.

## 2. Identity: when are two values the same?

Two values are the same value exactly when they are structurally identical under the rules of the algebra.

### Atom identity

```text
Atom(a) = Atom(b)
```

iff `a` and `b` are the same finite byte string.

No Unicode normalization. No numeric interpretation. No decoding. No compression equivalence. Exact bytes only.

### Sequence identity

```text
Sequence(x₀, ..., xₙ₋₁) = Sequence(y₀, ..., yₘ₋₁)
```

iff `n = m` and every corresponding element is the same value:

```text
xᵢ = yᵢ for all i
```

Order matters.

So:

```text
Sequence(Atom("a"), Atom("b"))
```

is not the same value as:

```text
Sequence(Atom("b"), Atom("a"))
```

### Map identity

Two maps are the same value iff they have the same finite domain and assign the same value to each key.

```text
Map M = Map N
```

iff for every value `k`:

```text
k ∈ dom(M)  exactly when  k ∈ dom(N)
```

and when `k` is present:

```text
M(k) = N(k)
```

Entry order does not matter.

So these are the same value:

```text
Map {
  Atom("a") -> Atom("1"),
  Atom("b") -> Atom("2")
}
```

and:

```text
Map {
  Atom("b") -> Atom("2"),
  Atom("a") -> Atom("1")
}
```

### Different constructors are never equal

An atom is never equal to a sequence.
A sequence is never equal to a map.
A map is never equal to an atom.

This remains true even when they are all “empty.”

---

## 3. Why this identity rule is forced

The foundation has no observer except the value itself.

So equality cannot depend on:

* source syntax;
* encoding bytes;
* storage address;
* object pointer;
* insertion order;
* chunking;
* compression;
* language runtime representation;
* schema;
* declared type;
* provenance;
* trust status;
* domain interpretation.

If equality were stricter than structural equality, it would smuggle in representation accidents. For example, two maps with the same entries but different insertion orders would become different values. That would make storage and transport details leak into reasoning and authority.

If equality were looser than structural equality, it would smuggle in consumer semantics. For example, treating `Atom("1")`, `Atom(0x01)`, and some integer representation as “the same” would require a built-in theory of numbers or text. Treating two differently structured logical formulas as equal would require a built-in logic. Treating two signature encodings as equal would require cryptographic policy.

Both are disallowed.

The only equality left is extensional structural equality.

Canonical encoding, hashing, content addressing, signing, diffing, and rendering may all depend on this equality, but they do not define it. A canonical encoding is an encoding of values; it is not the value model.

## 4. Inclusion justifications

| Included element                 | Necessary                                                                                                                                                                                                                         | Agnostic                                                                                                                                                    |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Finite valuehood**             | Without finiteness, transport, storage, deterministic equality, and canonical encoding become ill-defined or partial.                                                                                                             | Finiteness says nothing about reasoning, authority, schema, or storage policy. It only says a value can be fully present.                                   |
| **Immutability**                 | If values can change, identity across boundaries is not stable. A signed, stored, reasoned-over, or diffed thing could silently become another thing.                                                                             | No consumer should need foundational values to mutate. Consumers may model change by producing new values.                                                  |
| **Well-foundedness / no cycles** | Recursive equality and canonical representation must terminate. Cycles introduce object identity or reference semantics.                                                                                                          | Acyclicity is about valuehood, not about any particular consumer. Graphs can be represented explicitly above the foundation.                                |
| **Opaque byte atom**             | The model needs a leaf form that can carry uninterpreted finite data without forcing every scalar through a consumer-specific structure.                                                                                          | Bytes have no built-in meaning. Every consumer can preserve them without agreeing on text, numbers, cryptography, media, or schema.                         |
| **Ordered sequence**             | Ordered composition cannot be recovered from unordered structures without inventing indices or an encoding convention.                                                                                                            | Order is a primitive structural fact. It is not tied to any consumer’s interpretation.                                                                      |
| **Unordered map**                | Associative composition is a basic data shape. If omitted, every unordered record-like structure must be encoded as an ordered sequence, making arbitrary order part of identity or forcing private canonicalization conventions. | A finite partial function from values to values is generic. It does not imply records, objects, JSON, schemas, field names, databases, or authority claims. |
| **Arbitrary values as map keys** | Restricting keys to strings or atoms would privilege one scalar kind and force compound keys through ad hoc encodings.                                                                                                            | Keyhood is structural association, not naming. A key is just a value.                                                                                       |
| **Constructor disjointness**     | Without it, empty atom, empty sequence, and empty map could collapse; round-tripping would lose structure.                                                                                                                        | The constructors are the foundation’s only built-in distinctions. They do not encode domain types.                                                          |
| **Unique map keys**              | Duplicate keys require a policy: first wins, last wins, all preserved, error, merge. Those are not foundationally equivalent.                                                                                                     | A partial function is unambiguous. Multimaps and ordered pairs can be represented above.                                                                    |
| **Unbounded finite size**        | Fixed size limits would become permanent cross-system incompatibilities.                                                                                                                                                          | Resource limits are implementation policy, not value semantics.                                                                                             |

The strongest inclusion is the map. A purist could say atoms plus sequences are sufficient because maps can be represented as sorted sequences of pairs. I reject that for this brief. That moves unordered association out of value identity and into a convention. The purpose here is not merely to encode data; it is to define the shared thing being encoded. Ordered and unordered composition are different facts about data. The foundation should distinguish them.

## 5. Deliberate exclusions

### No booleans

`true` and `false` are not foundational values.

A reasoning system will certainly need truth values. Some authority system may need validity flags. Many tools will need predicates. But “truth” is not a property of a value as such.

A higher layer can define:

```text
Bool.true
Bool.false
```

using ordinary values. The foundation should not.

### No null

There is no built-in `null`.

Null usually mixes several ideas:

* absence;
* unit;
* unknown;
* error;
* intentionally blank;
* not applicable;
* database null;
* JSON null;
* bottom;
* optional none.

Those meanings diverge across consumers. The foundation should not bless one.

The empty sequence can serve as a unit in a higher convention, but it is not called null by the foundation. Absence from a map is also not a value; it is simply non-membership in that map’s domain.

### No numbers

No integers, decimals, floats, rationals, bigints, NaNs, infinities, negative zero, numeric promotion, precision, rounding mode, or canonical decimal form.

Numbers are where interchange formats often rot.

A foundation-level number would immediately force decisions about:

* integer size;
* signedness;
* arbitrary precision;
* decimal versus binary;
* floating-point behavior;
* NaN identity;
* `-0`;
* lexical forms;
* leading zeroes;
* scientific notation;
* normalization;
* comparison.

Those are not agnostic. They belong in numeric vocabularies above the foundation.

A higher layer can define exact integers, IEEE-style floats, decimals, rationals, field elements, tensor dtypes, or domain-specific numeric forms as values. But the foundation should not contain “number.”

### No text string

There is no built-in string.

Text is important, but not foundational. A built-in string forces decisions about:

* character repertoire;
* encoding;
* normalization;
* invalid sequences;
* versioning;
* collation;
* locale;
* case folding;
* grapheme boundaries;
* display equivalence versus byte equality.

The foundation has bytes. A text vocabulary can define UTF-8, normalization policy, language tags, or any other text contract above it.

This is intentionally austere. It prevents the foundation from inheriting every disagreement in the history of text processing.

### No symbols, names, URIs, namespaces, or identifiers

Names are values only when represented as values.

The foundation does not know whether an atom names a field, a person, a type, a rule, a hash algorithm, a namespace, or a URL. Naming systems belong above the foundation.

A vocabulary may define globally scoped identifiers. The value model should not.

### No type system or schema

There are no foundational types beyond the three constructors.

No record types.
No enums.
No optionals.
No unions.
No constraints.
No required fields.
No default values.
No schema evolution rules.

Schemas can themselves be represented as values. Validation is a consumer activity.

### No built-in tags

A tag constructor is tempting:

```text
Tagged(tag, payload)
```

I would not include it.

Tags are useful, but the foundation already has disjoint constructors and generic composition. A tagged value can be represented as a sequence or map under a vocabulary. Making tags foundational would invite the foundation to become a type registry.

The foundation should provide material from which tagging disciplines can be built, not choose one.

### No links, references, pointers, or content addresses

A content address is not a value primitive.

Storage will need hashes and links. Authority systems may sign hashes. Transport may chunk by hash. But dereference semantics, hash algorithms, mutability of targets, availability, trust, and collision policy are not properties of values as such.

A hash can be represented as an atom. A link object can be represented as a map. But the foundation should not contain “link.”

The value is the value. A reference to a value is another value interpreted by a storage layer.

### No canonical encoding

The value model must be canonically encodable, but the canonical encoding is not part of the value model.

This distinction matters.

A canonical encoding may say:

* how to mark constructors;
* how to encode lengths;
* how to sort map keys;
* how to reject duplicate map keys;
* how to stream large atoms;
* how to produce bytes for hashing.

Those are encoding rules. They must be deterministic and injective over values, but they are not themselves values.

The model should survive replacement of every concrete encoding.

### No hash identity

Two values are not the same because their hashes match. They are the same because their structures are equal.

A hash may be used as an implementation shortcut or storage address. It is not identity.

### No provenance, authorship, authority, trust, or attestation

The authority substrate will care deeply about:

* who asserted something;
* when they asserted it;
* under what key;
* under what policy;
* whether a signature verifies;
* whether a trust chain is acceptable.

None of that belongs in the value model.

An attestation is a value interpreted by the authority layer. Its validity is not a foundational property.

This is the same reason cryptographic signature schemes are excluded. A signature scheme may be essential to an authority system, but it is not agnostic.

### No logic, facts, rules, variables, or truth conditions

A reasoning system may represent terms, formulas, rules, substitutions, proofs, variables, quantifiers, and environments as values.

But the foundation should not know:

* what follows from what;
* whether a value is a fact;
* whether a rule is valid;
* how variables bind;
* whether two formulas are alpha-equivalent;
* whether two proofs prove the same thing.

A variable symbol can be represented as a value. Variable semantics belong to the reasoning system.

### No time

No timestamp, duration, clock, calendar, monotonic counter, version, or causality primitive.

Time is not a property of a value as such. A timestamp can be represented as a value under a time vocabulary. Clock semantics belong above the foundation.

### No global ordering or comparison

The foundation has sequence order and map membership. It does not have a total order over all values.

A canonical encoder may define an internal ordering to serialize map keys. A database may define an index order. A UI may sort values for display. None of those is foundational identity.

### No comments, whitespace, or source preservation

Concrete syntaxes may have comments, whitespace, field order, trailing commas, anchors, aliases, macros, or other presentational features.

Those are not values.

If preserving source form matters, represent the source form as data above the foundation. Do not burden the value model with it.

### No object identity or sharing

These are the same value:

```text
Sequence(x, x)
```

whether the two occurrences were represented with shared memory, duplicated memory, references, compression, or hash-consing.

Sharing is an implementation strategy. Object identity is not value identity.

### No graph primitive

Graphs are important, but graph identity is not simple. There are choices about node identity, edge identity, labels, direction, multiplicity, ordering, hyperedges, ports, attributes, and graph isomorphism.

A graph should be represented explicitly as values, for example with maps from node identifiers to edge lists. The graph layer can define its own equality.

The foundation remains acyclic and extensional.

### No errors, unknowns, bottoms, holes, or partial values

A value is complete.

Consumers may model unknowns, failures, deferred computations, optional fields, or partial information using values. But the foundation should not contain a privileged “unknown” or “error.”

### No resource limits

The foundation does not say:

* maximum atom length;
* maximum sequence length;
* maximum nesting depth;
* maximum map size;
* maximum canonical encoding length.

Implementations may impose limits. Protocol profiles may impose limits. Those are not value semantics.

## 6. Boundary rule for higher layers

Higher layers may define vocabularies over foundational values.

For example:

```text
Integer := Sequence(Atom("int"), sign, magnitude)
Text    := Sequence(Atom("text.utf8"), bytes)
Bool    := Atom("bool.true") | Atom("bool.false")
Time    := Sequence(Atom("time.utc"), seconds, nanos)
Link    := Sequence(Atom("link"), hash-algorithm, digest)
Claim   := Map { subject -> ..., predicate -> ..., object -> ... }
```

The exact encodings above are illustrative, not recommended. The point is structural: those concepts can be built from values without becoming foundational.

A higher layer may also define a domain equality stricter or looser than foundational equality. But then it must own that equality.

For example, a numeric layer may decide that two different decimal spellings denote the same number. The foundation will not. If the numeric layer wants content-addressing to respect numeric equality, it must canonicalize before producing the foundational value.

This is a crucial discipline:

```text
foundational identity = structural value identity
domain equivalence    = consumer-owned interpretation
```

Do not mix them.

## 7. Genuine forks

These are choices where reasonable designers could differ.

### Fork 1: byte strings versus bit strings

The model uses finite byte strings as atoms.

A more theoretically minimal model might use bit strings. That would be slightly more primitive. It would avoid the assumption that octets are the natural substrate.

I still lean byte strings.

Reason: the foundation is for interoperation between machines and systems, not pure mathematics. Byte strings are the universal practical substrate for storage, transport, signatures, compression, media, and executable data. Bit-level data can be represented above as:

```text
Map {
  Atom("bit-length") -> ...,
  Atom("bytes")      -> ...
}
```

Using bits instead of bytes would make the foundation marginally purer and substantially less convenient. This is a genuine fork, but byte atoms are the right practical freeze point.

### Fork 2: arbitrary map keys versus atom-only keys

The proposal allows any value to be a map key.

A simpler model could restrict map keys to atoms. That would make implementation easier and align with many object syntaxes.

I lean strongly toward arbitrary value keys.

Reason: atom-only keys privilege one naming discipline. They also force compound keys through ad hoc encodings, which is exactly the kind of drift the foundation is meant to prevent. If maps are finite associations from values to values, keyhood should not require a special scalar class.

Implementations that need hashable keys can hash canonical encodings internally. That is an implementation concern, not a semantic one.

### Fork 3: whether to include a set constructor

A set constructor would be clean:

```text
Set(Value*)
```

with no order and no duplicates.

I would not include it.

Reason: sets can be represented using maps to a conventional unit value, or by higher-layer vocabularies. More importantly, adding both set and map creates questions about whether a set is a map with unit values, whether they are distinct, and which collection forms deserve primitive status.

Map is the more general unordered association primitive. Set can live above.

### Fork 4: whether to include a tag constructor

A tag constructor would help define domain-specific variants cleanly.

I would not include it.

Reason: a tag constructor is dangerously close to a type system. The foundation should not contain a blessed extension mechanism with implied global tag semantics. Tags can be represented with sequences or maps under a vocabulary.

### Fork 5: whether to include map at all

The strictest possible model could be:

```text
Atom(bytes)
Sequence(Value*)
```

and represent maps as sorted sequences of pairs.

I do not accept that as the right answer for this brief.

It is sufficient for encoding, but not for value identity. If unordered association is represented as a sequence, either arbitrary order becomes part of identity or every consumer must agree on an external canonicalization rule. That recreates the translation boundary the foundation is supposed to eliminate.

So I acknowledge the fork, but classify map as forced by the goal of shared value identity rather than by bare representational completeness.

## 8. Stress test: new kinds of data

The model should not need to change when new data kinds appear. New kinds should be represented as new vocabularies over the same algebra.

### New scalar kind

Suppose a future system needs exact algebraic numbers, quantum amplitudes, finite field elements, or high-precision decimals.

The foundation does not grow a scalar.

The new layer defines a canonical representation using atoms, sequences, and maps. If it needs special equality, it canonicalizes or owns an equivalence relation above the foundation.

### New media kind

An image, audio stream, model checkpoint, tensor, CAD file, or genome can be represented as a map containing metadata values and byte atoms.

The foundation does not need to know pixels, sample rates, tensor shapes, or codecs.

### New authority mechanism

A new signature scheme, proof system, key format, or trust policy can be represented as values.

The foundation does not need to know whether a signature verifies. It only preserves the bytes and structure needed by the authority layer.

### New reasoning formalism

A new logic can represent terms, rules, binders, substitutions, and proofs as values.

The foundation does not need to know alpha-equivalence, unification, entailment, proof normalization, or model theory.

### New storage architecture

A new content-addressed store may chunk, compress, encrypt, hash, replicate, or cache values differently.

The foundation does not change. Storage transforms representations of values; it does not change value identity.

### New graph-like data

Graphs can be represented explicitly:

```text
Map {
  Atom("nodes") -> Sequence(...),
  Atom("edges") -> Sequence(...)
}
```

or in some more canonical graph vocabulary.

If graph isomorphism matters, the graph layer owns that equality. The foundation will not decide that two differently numbered graphs are the same.

## 9. The main weakness

The model refuses to represent non-finite or intensional entities directly.

If a future consumer says:

> “The value itself must be an infinite stream.”

or:

> “The value itself must be a live capability.”

or:

> “The value itself must be a function, and two functions are equal when observationally equivalent.”

then this foundation says no.

It can represent finite descriptions of streams, capabilities, functions, programs, proofs, or references. It cannot make those entities themselves foundational values.

I consider that a strength, not a defect. The moment the foundation admits behavior, liveness, authority, dereference, or non-finite equality, identity stops being stable across independent implementations.

The price of long-term interoperation is that the foundation only contains things whose equality can be determined from the value itself.

---

## 10. Practical consequences for encodings and implementations

Even though the proposal is not a wire format, it imposes obligations on any encoding that claims to carry these values.

A correct encoding must decode to exactly one foundational value.

A canonical encoding must encode each foundational value in exactly one way.

A map encoding must not let entry order affect the decoded value.

Duplicate map keys must not become an implementation-defined behavior. They must be rejected or normalized before a value exists.

A hash or content address must be over a canonical representation of the value, or otherwise specify exactly what value identity it commits to.

A renderer may choose any presentation, but presentation is not value identity.

A diff tool may choose any comparison strategy, but foundational equality remains structural equality.

A language binding may use native dictionaries, arrays, byte buffers, structs, or classes internally, but those are implementation choices. The abstract value is the finite term.

---

# Final position

Freeze the foundation as:

```text
Atom(bytes)
Sequence(values)
Map(value -> value)
```

with finite, immutable, well-founded, extensional structural identity.

Do not include numbers.
Do not include strings.
Do not include booleans.
Do not include null.
Do not include schemas.
Do not include tags.
Do not include links.
Do not include hashes.
Do not include signatures.
Do not include time.
Do not include logic.
Do not include provenance.
Do not include canonical encoding.

The foundation’s job is not to be pleasant, expressive, or self-describing in a domain sense. Its job is to be the stable shared substrate beneath systems that will disagree forever about meaning.

This model gives them exactly enough common ground to preserve the same value across boundaries, and little enough that it has a chance of surviving.
