## Thesis

I would freeze the shared value model as **finite immutable trees with byte-string atoms and ordered finite tuple nodes**.

Formally:

```text
Bytes  = all finite sequences of octets

Value  = Atom(Bytes)
       | Tuple(Value*)
```

where `Value*` is a finite ordered sequence of values, including the empty sequence.

That is the whole foundation.

No integers. No strings. No booleans. No maps. No sets. No records. No dates. No hashes. No references. No schemas. No signatures. No provenance. No types. No object identity. No evaluation. No reduction. No semantic normalization.

This is intentionally austere. It is not meant to be pleasant as an application data model. It is meant to be the **free, closed, well-founded substrate** on which application data models can be built without smuggling their semantics into everyone else’s foundation.

A useful type-theoretic description is:

```text
Value is the initial algebra μX. Bytes + List(X)
```

That initiality matters. A consumer can interpret values by giving an interpretation of atoms and tuples. The foundation itself commits to nothing else.

---

# 1. Core semantics

A value is a **closed, finite, immutable, well-founded term** generated by two constructors.

## Constructor 1: `Atom(b)`

`b` is a finite byte string.

Examples:

```text
Atom("")
Atom("hello")
Atom(0x00ff7a)
```

An atom is not a string, not a symbol, not a number, not a blob-with-MIME-type. It is just finite uninterpreted octets.

The only foundation-level fact about an atom is its exact byte sequence.

## Constructor 2: `Tuple(v₁, …, vₙ)`

A tuple is a finite ordered sequence of values.

Examples:

```text
Tuple()
Tuple(Atom("name"), Atom("Ada"))
Tuple(Atom("point"), Atom("x"), Atom("10"), Atom("y"), Atom("20"))
Tuple(Tuple(Atom("a"), Atom("b")), Atom("c"))
```

A tuple is not a list in the Lisp sense, not an array with update semantics, not a record, not a set, and not a constructor application with a blessed tag. It is only finite ordered composition.

The arity is part of the value. Therefore:

```text
Tuple(Atom("a"), Atom("b"))
```

is not the same as:

```text
Tuple(Atom("a"))
Tuple(Atom("a"), Atom("b"), Atom("c"))
Tuple(Tuple(Atom("a"), Atom("b")))
```

There is no implicit flattening, associativity, sorting, or normalization.

## Finiteness and well-foundedness

Values are finite trees.

There are no cyclic values. There are no infinite values. There is no graph sharing in the semantics.

An implementation may store a value as a DAG internally, but that sharing is not part of the value. These two implementation layouts denote the same value:

```text
Tuple(x, x)
```

and

```text
Tuple(copy_of_x, another_copy_of_x)
```

provided the two occurrences are structurally equal.

A cyclic graph, a lazy stream, a database handle, or a live object can be represented by a value only through some finite description or reference chosen by a higher layer.

## No invalid values

Every term generated by the grammar is a valid value.

There are no foundation-level well-formedness predicates such as “the first element of this tuple must be a tag,” “this byte string must be UTF-8,” or “this tuple must have even length.”

Those are schema-level or consumer-level facts.

# 2. Identity: when are two values the same?

Two values are the same value by **structural equality over the two constructors**.

Precisely:

```text
Atom(b) = Atom(c)
    iff b and c are the same byte string

Tuple(v₁, …, vₙ) = Tuple(w₁, …, wₘ)
    iff n = m
    and for every i, vᵢ = wᵢ

Atom(_) ≠ Tuple(_)
```

That is the only equality.

No other equations hold.

So all of the following are distinct values:

```text
Atom("1")
Atom("01")
Atom(0x01)
Tuple(Atom("1"))
Tuple(Atom("number"), Atom("1"))
Tuple(Atom("number"), Atom("01"))
Tuple(Atom("integer"), Atom("1"))
```

Likewise:

```text
Tuple(Atom("a"), Atom("b"))
```

is distinct from:

```text
Tuple(Atom("b"), Atom("a"))
```

and from:

```text
Tuple(Tuple(Atom("a"), Atom("b")))
```

## Why this equality is forced

The foundation has only two observations available:

1. Is the value an atom or a tuple?
2. If atom, what exact bytes?
3. If tuple, what arity and what children?

Therefore equality can only be equality over those observations.

Any stronger equality would erase information. For example, if tuple order were ignored, then consumers could not faithfully represent ordered pairs, argument lists, syntax trees, paths, byte chunks, or sequences without adding another ordering mechanism elsewhere.

Any weaker equality would introduce representation identity. For example, if two identical trees stored at different addresses were considered different, the model would no longer be a value model. It would be an object model.

Any semantic equality would import non-foundational meaning. For example:

```text
Atom("1") = Atom("01")
```

would require a theory of numbers or strings.

```text
Tuple(Atom("map"), Tuple(k, v), Tuple(k, v))
```

being invalid or duplicate-collapsed would require a theory of maps.

Unicode normalization, integer normalization, rational normalization, timezone normalization, hash equivalence, alpha-equivalence, and schema-aware equality all belong above the foundation.

So the foundation uses the only equality that is both total and agnostic: **constructor identity plus recursive structural equality**.

In PL terms, this is the equality of the free term algebra, with no quotient.

# 3. Justification of every inclusion

## Inclusion: immutable value semantics

A value is not a cell, object, promise, stream, capability, actor, database row, or mutable location.

### Necessary

If a value could change while remaining “the same value,” consumers could not safely share identity. Storage, reasoning, authority, and tooling would disagree about whether they had the same thing before and after mutation.

### Agnostic

Immutability is true of values as values. Consumers may model change, history, replacement, revocation, or versioning, but those are relations between values, not mutation of a value itself.

---

## Inclusion: finiteness

Every value is finite.

### Necessary

The shared substrate must support storage, transport, comparison, hashing, rendering, diffing, and attestation over concrete data. Infinite values make total equality, transport, and persistence non-uniform or partial.

A consumer may reason about infinite structures, but the thing handed across the substrate must be a finite description.

### Agnostic

Finiteness is not specific to reasoning, authority, or storage. It is a condition for being a concrete transmissible value.

---

## Inclusion: well-founded tree structure

Values are trees generated inductively. No cycles. No semantic sharing.

### Necessary

Well-foundedness gives structural induction, structural recursion, and decidable equality. Without it, equality becomes a coinductive or graph-theoretic matter, and consumers must agree on bisimulation, sharing, reference identity, and cycle treatment.

### Agnostic

Acyclic tree-ness is a property of the foundational representation. Graphs, cycles, references, and sharing are representable above the foundation as explicit data.

For example, a graph can be encoded as:

```text
Tuple(
  Atom("graph/v1"),
  Tuple(Atom("node"), Atom("n1")),
  Tuple(Atom("node"), Atom("n2")),
  Tuple(Atom("edge"), Atom("n1"), Atom("n2"))
)
```

The foundation need not itself be a graph.

---

## Inclusion: byte-string atoms

Atoms are finite byte strings.

### Necessary

The foundation needs some irreducible carrier of uninterpreted data. Without atoms, the only values would be unlabeled tree shapes. That cannot carry names, payloads, external bytes, hashes, signatures, source text, serialized media, identifiers, or domain literals.

The atom carrier must have exact equality and finite representation. Byte strings are the smallest practical universal substrate for that.

### Agnostic

A byte string is not a number, string, hash, image, public key, timestamp, or schema identifier. It can carry any of those only when a higher layer says so.

The foundation commits only to exact octets.

---

## Inclusion: ordered finite tuples

Tuples are finite ordered sequences of values.

### Necessary

Atoms alone collapse the model into “everything is a private serialization.” That would recreate the boundary problem: each consumer would need to parse and reserialize according to its own conventions.

A shared substrate needs one common way to compose values into larger values while preserving inspectable structure. Ordered finite product is the minimal such composition.

Order is necessary because products have distinguishable positions. Without distinguishable positions, the foundation cannot directly represent pairs, argument order, syntax trees, paths, sequences, or ordered evidence chains.

### Agnostic

A tuple does not say what its positions mean. It does not say the first position is a tag. It does not say the tuple is a list, record, constructor, assertion, rule, map entry, or function call.

Consumers may impose those interpretations, but the foundation does not.

---

## Inclusion: empty atom and empty tuple

Both of these are values:

```text
Atom("")
Tuple()
```

They are distinct.

### Necessary

Closure under finite byte strings includes the empty byte string. Closure under finite tuples includes the zero-length tuple.

Removing either creates arbitrary edge cases and partiality.

### Agnostic

Neither is “null,” “false,” “unit,” “empty list,” or “missing.” Higher layers may assign such meanings, but the foundation merely contains the zero-length cases of its two constructors.

---

## Inclusion: constructor disjointness

Atoms and tuples are disjoint.

```text
Atom(b) ≠ Tuple(...)
```

for all `b`.

### Necessary

Without constructor disjointness, equality would need equations between raw bytes and structure. That would amount to choosing a serialization as semantic equality, which would entangle the abstract value model with an encoding.

### Agnostic

The distinction between atom and tuple is the foundation’s only shape distinction. It carries no consumer-specific meaning.

---

## Inclusion: no built-in size limits

The model permits all finite byte strings and all finite tuples.

Implementations may impose practical limits, but those are not semantic.

### Necessary

A foundational semantic model should not bake in one implementation’s memory, transport, database, or VM limits. If limits are semantic, then values valid in one consumer may be invalid in another.

### Agnostic

Resource limits are operational policy. They are not facts about values as such.

---

# 4. What is deliberately excluded

This is the important part. Most tempting primitives should be rejected.

## Excluded: booleans

No built-in `true` or `false`.

Reason: booleans are useful, but not foundational. A higher layer can encode them as:

```text
Tuple(Atom("bool/v1"), Atom("true"))
Tuple(Atom("bool/v1"), Atom("false"))
```

or any other agreed convention.

They fail the necessity test. Consumers can agree on booleans inside a schema or protocol without making every value consumer inherit them.

---

## Excluded: null / none / missing

No built-in null.

Null is notoriously overloaded: absent field, unknown value, explicit empty value, bottom, unit, SQL null, JSON null, tombstone, optional none.

It fails the agnostic test. Different consumers absolutely will want it differently.

Use a higher-level encoding.

---

## Excluded: numbers

No integers, naturals, rationals, decimals, floats, bigints, NaNs, infinities, or numeric tower.

Numbers are the classic trap.

Integer equality seems harmless until one must choose encodings, signs, leading zero treatment, bounds, canonical forms, and arithmetic semantics.

Rationals require normalization:

```text
1/2 = 2/4
```

Decimals raise scale questions:

```text
1.0 = 1.00?
```

Floats bring NaNs, signed zero, rounding, payload bits, and platform behavior:

```text
NaN = NaN?
0.0 = -0.0?
```

These are not foundational choices. They are domain choices.

A numeric protocol can define canonical numeric values above the foundation. The foundation should not.

---

## Excluded: text strings

No built-in text.

Text seems universal, but text equality is not universal.

Questions immediately appear:

```text
Is UTF-8 required?
Are invalid byte sequences allowed?
Is Unicode normalization applied?
Are canonically equivalent sequences equal?
Are case-folded strings equal?
Are locale rules involved?
Are grapheme clusters observable?
```

The foundation should only preserve bytes. Text is an interpretation of bytes under a schema.

So:

```text
Atom(0x48656c6c6f)
```

may be interpreted by a higher layer as UTF-8 `"Hello"`, but the foundation does not say so.

---

## Excluded: symbols, identifiers, names, namespaces

No built-in symbol type.

Symbols require a naming discipline. Are they global? Local? Interned? Case-sensitive? URI-like? Content-addressed? Authority-scoped? Human-readable? Versioned?

All of that belongs above the foundation.

A symbol can be represented as an atom or tuple by convention:

```text
Atom("example.com/foo")
Tuple(Atom("symbol/v1"), Atom("example.com"), Atom("foo"))
```

But the foundation does not bless one.

---

## Excluded: records

No built-in records or objects.

A record brings field names, duplicate-field policy, field order, absent-field behavior, default values, schema evolution, and equality rules.

For example, are these the same?

```text
{ x: 1, y: 2 }
{ y: 2, x: 1 }
```

A storage layer, renderer, diff tool, and reasoning engine may reasonably answer differently depending on context.

So records are encoded above the foundation, usually as tuples.

---

## Excluded: maps

No built-in maps.

Maps impose extensional equality, key equality, duplicate-key handling, and order irrelevance.

A map can be represented as:

```text
Tuple(
  Atom("map/v1"),
  Tuple(key1, value1),
  Tuple(key2, value2)
)
```

A map schema can require entries to be sorted and keys to be unique. But that is a map schema, not the value foundation.

Maps fail the agnostic test because consumers differ on whether insertion order matters, whether duplicate keys are invalid or last-wins, and whether key equality is structural or interpreted.

---

## Excluded: sets

No built-in sets.

Sets impose duplicate elimination and order-insensitive equality.

That is a quotient over structure. Quotients are expensive in a foundation because they erase distinctions some consumers may need.

A set protocol can encode a canonical sorted tuple of elements. The foundation should not decide that all unordered collections are sets.

---

## Excluded: tagged constructors

No built-in ADT constructor namespace such as:

```text
Point(x, y)
Some(v)
None
```

At first this is tempting to a PL designer. But constructor identity requires a namespace and a theory of names. That is not foundational.

Constructor-like values can be represented by convention:

```text
Tuple(Atom("Point"), x, y)
Tuple(Atom("Some"), v)
Tuple(Atom("None"))
```

But the foundation does not know that the first element is a tag.

---

## Excluded: type system

No built-in types, kinds, schemas, refinements, or validation rules.

The foundation is prior to typing. Types classify values; they are not needed to define what a value is.

A type system can itself be represented as values. A schema can be a value. A proof that a value inhabits a schema can be a value. But none of that belongs in the value model itself.

This is critical: **“well-typed” is not the same as “is a value.”**

---

## Excluded: logical truth, rules, and inference

No propositions, predicates, variables, binders, quantifiers, substitutions, proof terms, or rule semantics.

A reasoning system can encode all of these as values, but the foundation must not know what follows from what.

Reasoning semantics is not agnostic. Different reasoning systems will have different logics, equality theories, variable binding disciplines, and proof standards.

---

## Excluded: authority, attestation, and trust

No built-in notion of author, signer, issuer, credential, revocation, delegation, validity, or trust chain.

The authority substrate will absolutely need these. That does not make them foundational.

They fail the agnostic test. A reasoner may treat an attestation as an ordinary tuple. A storage layer may treat it as bytes and structure. A trust engine may interpret it as an assertion under a policy.

A signature is just data at the foundation level, for example:

```text
Tuple(
  Atom("signature/v1"),
  algorithm,
  public_key,
  payload,
  signature_bytes
)
```

The foundation should not know which algorithms exist or what makes a signature valid.

---

## Excluded: cryptographic hashes and content addresses

No built-in hash, CID, digest, Merkle link, or addressing primitive.

A storage system may define content addressing over values. But hash algorithms change, encodings change, multihash formats change, and different systems may address different projections.

A digest can be represented as bytes. A link can be represented as a tuple. But “this value denotes that other value” is not a fact of the value model.

---

## Excluded: time

No timestamps, durations, calendars, clocks, time zones, intervals, or validity periods.

Time is not foundational. It is full of policy: clock source, leap seconds, calendar system, timezone database, precision, uncertainty, monotonicity, and validity semantics.

Time values can be encoded by protocols. The foundation should not define them.

---

## Excluded: locations and references

No pointers, object IDs, database keys, URLs, paths, handles, capabilities, or dereference semantics.

A reference is not just a value; it is a relation between a value and some external resolution process.

The reference token can be represented as a value. Dereferencing is outside the foundation.

---

## Excluded: object identity

No nominal object identity.

Two structurally equal values are the same value. There is no hidden identity bit.

If some consumer needs two equal-looking but distinct entities, it must put the distinction into the value explicitly, for example with an identifier field.

---

## Excluded: graph sharing

No semantic sharing.

This:

```text
Tuple(x, x)
```

does not mean “the same object occurs twice.” It means the same value occurs twice.

If sharing matters, encode it explicitly as a graph with node identifiers.

---

## Excluded: cycles

No cyclic values.

Cycles require graph identity or coinductive equality. Neither is agnostic.

Represent cyclic structures as finite graph descriptions.

---

## Excluded: comments, annotations, metadata

No comments, source locations, formatting, display names, labels, or annotations.

Tools may preserve annotations in higher-level values, but the foundation should not have “non-semantic metadata.” If it is in the value, it affects equality. If it does not affect equality, it is not part of the value.

Trying to have both is a common source of drift.

---

## Excluded: canonical serialization

The value model is not a byte-level serialization format.

A canonical serialization is useful, especially for hashing and transport. But it is a representation of values, not the definition of values.

I would standardize a canonical codec adjacent to this model, but I would not confuse the codec with the value semantics. The semantic identity of a value is structural equality, not equality of some accidental wire representation.

A codec must be injective and preferably canonical. But codecs are artifacts. Values are the abstract trees.

---

## Excluded: total ordering

No built-in global ordering over all values.

A lexicographic order could be defined easily:

```text
Atom before Tuple
bytes lexicographic
tuples lexicographic by children
```

But that order would be arbitrary. Useful, yes. Foundational, no.

Map encodings, set encodings, databases, and diff tools may define orders. The foundation only defines equality.

---

# 5. Genuine forks

Some choices are forced by the brief. Others are not. I would separate them carefully.

## Forced: structural equality

I regard this as forced.

Once values are immutable, uninterpreted, and shared across consumers, equality cannot depend on consumer interpretation. It must be structural equality over the constructors.

Any quotient imports semantics. Any nominal identity imports allocation or authority. Any representation identity breaks value semantics.

---

## Forced: no rich scalar primitives

I regard this as forced.

Integers, strings, booleans, timestamps, floats, and identifiers all seem attractive, but each brings equality and normalization commitments. Those commitments are not agnostic.

The foundation should provide a carrier for them, not define them.

---

## Forced: no maps or sets

I regard this as forced under the inclusion filter.

Maps and sets are not just data structures. They bring quotient equality: order irrelevance, duplicate policy, key equality, and canonicalization. Those are higher-level semantics.

Ordered tuples can represent maps and sets. The reverse is not true without smuggling in indices or labels.

---

## Genuine fork: bytes versus bits

The mathematically purer atom carrier is finite bit strings.

I lean byte strings.

Reason: modern storage, transport, cryptography, files, memory, and encodings are octet-based. A bit-string foundation would either add complexity everywhere or immediately be packed into bytes by convention.

This is not logically forced. It is an engineering choice. But it is a good one.

---

## Genuine fork: n-ary tuples versus binary pair plus unit

A purist could define:

```text
Value = Atom(Bytes) | Unit | Pair(Value, Value)
```

and encode tuples by nesting.

I lean n-ary tuples.

Reason: binary pairs force an arbitrary associativity convention:

```text
(a, (b, c))
((a, b), c)
```

Those are structurally different. If almost everyone wants finite sequences anyway, making finite arity primitive avoids pointless encoding bureaucracy.

This is still one product constructor: finite ordered product. It does not add maps, records, or types.

---

## Genuine fork: `Atom + Tuple` versus `Node(label, children)`

Another plausible foundation is:

```text
Value = Node(Bytes, Value*)
```

Then atoms are just nodes with zero children.

I reject it, but it is a real fork.

My reason: it forces every composite value to carry a byte label. That makes constructor naming feel foundational. But tags and labels are exactly the kind of thing I want higher layers to own.

With `Atom + Tuple`, a tagged node is easy:

```text
Tuple(Atom("tag"), child1, child2)
```

but untagged product is also available.

So I prefer the strictly less opinionated form.

---

## Genuine fork: whether to standardize a canonical codec alongside the value model

I would standardize one, but not make it part of the semantic core.

For storage and content addressing, a canonical byte encoding is extremely useful. But cryptographic and transport machinery evolves. The abstract value model should not be held hostage to one wire format.

The foundation should say:

```text
These are the values.
This is equality.
```

A separate codec specification can say:

```text
Here is the canonical way to encode them as bytes for this generation of infrastructure.
```

The codec may be frozen too, but it should be conceptually subordinate.

---

## Genuine fork: whether to expose a standard total order

I lean no.

A total order is useful for deterministic encodings of sets and maps. But any such order is arbitrary and not required for the value model itself.

If a higher-level map schema wants canonical ordering, it can define one. A common library can provide a conventional structural ordering. But foundation-level equality should not become foundation-level ordering by inertia.

---

# 6. Normal forms and canonicality

The foundation should have **no reduction relation**.

A value is already in normal form because it is a constructor tree. There are no equations such as:

```text
Tuple(Atom("int"), Atom("01")) = Tuple(Atom("int"), Atom("1"))
Tuple(Atom("set"), a, b) = Tuple(Atom("set"), b, a)
Tuple(Atom("rat"), Atom("2"), Atom("4")) = Tuple(Atom("rat"), Atom("1"), Atom("2"))
```

Those may be true inside particular higher-level domains, but not in the foundation.

This is the key discipline: if a consumer wants an extensional domain, it must define a **canonical embedding** into foundational values.

For example, a rational-number layer may say:

```text
A rational is encoded as:
Tuple(Atom("rational/v1"), numerator, denominator)

with:
- denominator positive
- numerator and denominator coprime
- integers encoded by some specified integer encoding
```

Then `2/4` is not equal to `1/2` at the foundation. Instead, the rational layer must normalize `2/4` into the canonical foundational value for `1/2`.

That is exactly where normalization belongs: at the layer that owns the equality theory.

# 7. How consumers build on it

## Reasoning system

The reasoner can treat values as syntax.

Facts, rules, predicates, terms, substitutions, proofs, and environments can all be encoded as values.

For example:

```text
Tuple(
  Atom("fact/v1"),
  Tuple(Atom("parent"), Atom("alice"), Atom("bob"))
)
```

But the foundation does not know this is a fact. It is just a tuple.

The reasoner may define additional equality theories internally, but when it hands data to another system, the handed object is still a structural value.

## Authority substrate

The authority system can encode assertions, signatures, keys, delegations, revocations, and trust chains as values.

For example:

```text
Tuple(
  Atom("assertion/v1"),
  issuer,
  subject,
  claim,
  evidence
)
```

Again, the foundation does not know what makes it valid. Validity is authority-layer semantics.

## Storage and transport

Storage can persist values by serializing the tree. Transport can move values by encoding the tree.

Content addressing can hash a canonical serialization of a value. But the hash is not the value’s identity. The value’s identity is structural equality.

## Tools

Renderers, diff tools, inspectors, and transformers can operate generically on atoms and tuples without understanding domain semantics.

A structural diff can always be defined. A semantic diff can be added by a schema-aware layer.

# 8. Why not use an existing richer model?

## Not JSON

JSON has strings, numbers, booleans, null, arrays, and objects. Its numbers are underspecified for many purposes, object field order is awkward, duplicate names are problematic, and strings impose Unicode decisions.

JSON is a useful interchange format, not a foundational value algebra.

## Not CBOR / MessagePack / Protobuf

Those are serialization or schema systems. They contain historical and operational choices about encodings and scalar types.

A serialization can carry this value model. It should not define it.

## Not RDF

RDF commits to triples, IRIs, blank nodes, literals, graph semantics, and a particular webby theory of naming.

That is far above the foundation.

## Not “everything is bytes”

Pure bytes are too little. They make structure private. If all structure is hidden inside opaque encodings, every boundary becomes a parse/convert boundary again.

The foundation needs shared composition, not just shared payload.

## Not “everything is a map”

Maps are too much. They commit to key-value structure and extensional equality. Many values are not maps, and many consumers need order.

# 9. Longevity stress test

The model survives new data kinds by refusing to classify data kinds foundationally.

Suppose a future consumer needs quantum circuits, legal contracts, neural embeddings, biological sequences, proof certificates, simulation states, credentials, 3D scenes, or something we do not yet have a name for.

The foundation does not grow. The new domain defines an encoding into values.

Usually that encoding has the shape:

```text
Tuple(domain_tag, version_tag, payload...)
```

For example:

```text
Tuple(
  Atom("example.org/quantum-circuit/v1"),
  gates,
  wires,
  measurements
)
```

The domain may define its own canonical forms, validation rules, equivalences, and interpretation. But the shared substrate still only sees atoms and tuples.

This gives longevity because the foundation is not a catalog of known data types. It is a universal syntax of finite data.

## New scalar domains

A new scalar domain is represented by bytes plus a tag.

Examples:

```text
Tuple(Atom("uuid/v1"), Atom(...16 bytes...))
Tuple(Atom("decimal/v1"), sign, coefficient, exponent)
Tuple(Atom("utf8-text/v1"), Atom(...bytes...))
```

The scalar domain owns its equality.

## New structured domains

A new structured domain is represented by tuples.

Examples:

```text
Tuple(Atom("matrix/v1"), rows, columns, entries)
Tuple(Atom("proof/v1"), system, conclusion, derivation)
Tuple(Atom("policy/v1"), clauses...)
```

The structure is still inspectable by generic tools.

## New graph-like domains

Graphs are encoded explicitly:

```text
Tuple(
  Atom("graph/v1"),
  nodes,
  edges
)
```

If the graph has cycles, those cycles exist in the graph described by the value, not in the value itself.

## New authority or cryptographic schemes

They are just new protocols over bytes and tuples.

No foundation change is needed when a signature scheme, hash function, credential format, or trust model changes.

## New equality theories

They are handled by canonical embedding or consumer-level equivalence.

The foundational equality remains structural.

This is essential. If the foundation admits new equality theories over time, old consumers and new consumers will silently disagree about identity.

---

# 10. The main weakness

The model cannot directly contain infinite, live, effectful, or externally mutable things.

It can contain only finite descriptions of them.

So if a future system says:

> “I need a value that is literally this live sensor stream,”

the answer is no. The foundation can represent:

```text
Tuple(Atom("stream-reference/v1"), endpoint, parameters)
```

or:

```text
Tuple(Atom("stream-snapshot/v1"), samples...)
```

but the live stream itself is not a value.

I consider that a feature, not a bug. The alternative is to pollute value identity with time, effects, authority, reachability, and observation.

A foundational value should be something one can hand to another party and have it remain itself.

---

# 11. Final proposal, compressed

Freeze this:

```text
Bytes  = finite octet strings

Value  = Atom(Bytes)
       | Tuple(Value*)
```

with:

```text
Atom(b) = Atom(c)
    iff b = c

Tuple(xs) = Tuple(ys)
    iff xs and ys have the same length
    and all corresponding elements are equal

Atom(_) ≠ Tuple(_)
```

and with these semantic commitments:

```text
finite
immutable
well-founded
closed
untyped
uninterpreted
no hidden identity
no quotient equality
no mutation
no references
no schemas
no consumer-specific primitives
```

Everything else is built above it.

The foundation should be boring enough to survive. Its job is not to make common things convenient. Its job is to make disagreement explicit. Richer layers may define numbers, text, maps, records, signatures, rules, types, dates, names, and trust. But when those layers exchange data, the exchanged thing is always the same kind of thing:

a finite structural value made of bytes and tuples.
