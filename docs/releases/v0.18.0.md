# ontos v0.18.0

ontos now specifies how its values are written as JSON, in two profiles, and ships them in
all four languages. Deep values also stop breaking rendering, equality and hashing in three
faces. The value model, structural identity, the `ontos-codec-v1` bytes, decoding and its
limits are unchanged.

## Two JSON projections of ground values

Decided in [design record 0010](../design/0010-json-projections.md), after
[consultation 0001](../consults/0001-reversible-json-projection.md) (ontos issue 33). Both
profiles are value-only: neither needs a type to read or write a value.

- **[`ontos-total-json/1`](../spec/ontos-total-json.md)** is the authoring notation,
  `{"atom":"<hex>"}` | `{"tuple":[…]}`, now a named profile with a full reading and writing
  contract. It is total over every ontos value.
- **[`ontos-readable-json/1`](../spec/ontos-readable-json.md)** writes the common ground
  values as ordinary JSON: `null`, booleans, strings, integers within ±(2⁵³ − 1), arrays and
  text-keyed objects. Everything else goes in one reserved envelope, `{"$ontos": [tag, …]}`,
  with the tags `bytes` (canonical base64), `int`, `decimal`, `map`, `set`, `compound` and
  `raw` (the total form). It is total too, and it is what generated bindings use to present
  values.

Both read source **bytes** with their own strict reader, in fixed stages and a fixed check
order. A refusal is the same in every language: a stable code, a typed path, a UTF-8 byte span
and, for a limit, its kind. Each profile has its own limits with a derived JSON depth. The
writers are deterministic and mirror the readers, and the readable reader can return each
value's origin in the source text. JSON is a presentation: identity, hashing and signing still
use the codec bytes of the recovered value.

All four pass the shared vectors in `projection/json/vectors` (89 total, 248 readable cases).
Every CI run also checks them against an independent reference implementation on freshly
generated inputs.

## The command line

The four `ontos` CLIs now read `--from-json` and write `--format json` values through these
libraries, and accept **`--json-profile total|readable`**. The default is `total`, so every
existing invocation behaves exactly as before. Readable input is read from stdin only
(`--from-json -`): a lossy channel such as Node's argv cannot carry it. Refusals keep the
CLI's existing codes (`invalid_json`, `limit_exceeded`). See [ontos-cli](../spec/ontos-cli.md),
"JSON profiles". The TypeScript CLI now also takes a `--from-json` argument that begins with
`-` as the text, as the other three do.

## Deep values: rendering, equality and hashing

A value nested as deep as the codec's default decoder accepts (1024 levels) could not always be
logged, compared or hashed:

- **Python:** `str()` and `repr()` raised RecursionError from about 900 levels, and `==` and
  `hash()` from about 1000. So `decode(b) == decode(b)` failed on a valid value, and such a value
  could not be a dict key.
- **TypeScript:** `toString` threw from about 5000 levels, and `equals` from about 100,000.
- **Go:** `String()` took time in the square of the depth (22 s at 100,000 levels), and `Equal`
  overflowed the goroutine stack at extreme depths.

All of these now walk an explicit stack. Results are unchanged: the same strings, the same
equality, and in Python **the same hash values**, so existing dicts and sets keep agreeing.
`JSON.stringify(value)` on a deep TypeScript value still meets V8's own recursion limit.

## Also in this release

- **32-bit coverage:** the whole root Go module, the JSON projections included, now runs at
  `GOARCH=386` in CI, and the Rust JSON crate runs on wasm32.
- **Release tooling:** the npm provenance signer retries a Sigstore transparency-log conflict
  (409) with a fresh signature. Both v0.17.1 rehearsals had met one.

## Upgrade

Every published package carries version `0.18.0`, a minor release. The new packages are
additions, and nothing in the existing ones changes shape. In Rust, a `0.17` core and a `0.18`
core are different `Value` types, so move every ontos crate together. The root Go tag `v0.18.0`
and the nested tags `projection/deixis/go/v0.18.0` and `wire/go/v0.18.0` name the same release
commit.
