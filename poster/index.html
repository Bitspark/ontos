§00

What crosses the boundary

The seam

Nothing leaves ontos except bytes. Four implementations exist; none of them is the reference. What they must agree on is not a signature, a class layout, or an error type — it is the exact octets, because arche takes an Ed25519 signature over them and logos hashes them into proof-DAG citations. Two cores that encoded the same value differently would make a signature verify in one and fail in the other.

What is published. The value-model libraries, to each language's public registry, with no credential needed: core, codec, data and data-json as @bitspark/ontos-* on npmjs, as bitspark-ontos-* on crates.io, and as packages of one Go module, github.com/bitspark/ontos. Every lane carries the same release number. The Python implementation is a stdlib-only validation lane, source only, registered as one more --impl on the conformance harness.

What is deliberately not published. The ontos CLI, in every language at once: the TS package is "private": true, the Rust crate is publish = false, the Go build is go install, and the Python lane has no packaging manifest to suppress. Nothing imports the CLI — you run it, you don't depend on it.

§01

The floor: two constructors, and nothing else

ontos/core · L0 · frozen

The set of values V is the least set closed under two constructors — equivalently the initial algebra μX. Bytes + List(X). There is no third kind of value: no nil, no variable, no number, no string, no map, no reference, no label slot. 

-- the whole value setAtom(b)              ∈ V    for every finite byte string bTuple(v₀, …, vₙ₋₁)   ∈ V    for every finite n ≥ 0 and all vᵢ ∈ V-- the whole identity relationAtom(b) = Atom(c)              iff  b and c are the same octetsTuple(x₀…xₘ₋₁) = Tuple(y₀…yₙ₋₁) iff  m = n and xᵢ = yᵢ, recursivelyAtom(_) ≠ Tuple(_)             always — the constructors are disjoint
  • Finite — finitely many tuples, each of finite arity, atoms of finite length. Nothing infinite or lazy.
  • Well-founded — a finite tree, never a graph. No value contains itself.
  • Immutable — "modifying" a value produces a different value.
  • Closed / context-free — no address, owner, creation time, validity, or provenance travels inside a value.
  • Ground — every value is whole. There is no hole, placeholder, or unknown. The variable is precisely what L0 excludes.
  • Atom bytes are uninterpreted — not text, not a number, not a hash, not a key. L0 commits only to which exact octets are present.
  • Order and arity are the value — no implicit flattening, sorting, or de-duplication.
  • Atom("") ≠ Tuple() — empty bytes and the empty tuple are different values. Neither is "null."
  • No object identity — no memory address, allocation history, or hidden identity bit. Structure is all there is.
  • Identity is never redefined above — every higher layer inherits it unchanged, and MUST NOT restate it.

§02

The bytes: two tags, length-prefixed, shortest form

ontos-codec-v1 · frozen · security-critical

This is the entire encoding. Not an excerpt — the whole normative byte mapping fits in two lines, and those two lines are immutable: a change ships as ontos-codec-v2 with an explicit migration, never as an edit to v1, because every signature and every hash in the stack above is taken over these bytes. Upgrading ontos therefore never changes the bytes of a value you already store, hash or sign.

§02.1   The tag set is closed

{0x00, 0x01} is the complete tag set. Every other byte is reserved, and a decoder MUST reject it as unknown_tag. In particular there is no variable tag — ontos values are ground and the codec cannot encode a variable. A consumer that needs one (logos's Var) must do it in its own codec, and MUST NOT redefine 0x00 or 0x01.

§02.2   What a conforming codec owes you
  • Determinism — encode(v) yields exactly one byte string.
  • Round-trip — decode(encode(v)) = v, for every value.
  • Injectivity — distinct values encode to distinct bytes.
  • Canonical rejection — a decoder MUST reject any byte string that is not the canonical encoding of some value, so that "valid encoding" and "canonical encoding" coincide. This is what lets a hash over the bytes stand in for the value.
  • A total order falls out — because the encoding is canonical, injective and prefix-free, lexicographic comparison of encodings totally orders all values. That order is what map and set sort by. It is a codec-derived convenience, not part of L0 identity.
Rejection codes — normative; the human message is not

Max decode depth is 1024 in all four cores — the one limit that could bite a valid input is harmonized. The host-width ceilings that do differ (263−1 Go, usize::MAX Rust, 253−1 TypeScript, none Python) cannot: no core can be handed a buffer longer than its own ceiling, so a length or arity past it declares more bytes than follow. The cores then differ only on which rejection fires for an input that is already truncated everywhere — never on whether it is valid.

§03

One value, all the way down

worked example · verified output

The integer zero. Ten octets. Read left to right, the tape below is the L0 tree above, and nothing else — no framing, no schema, no version header inside the value.

Authoring notation in, canonical bytes out, then evidence about those bytes, then the digest of those bytes. Every line below was run against a build of cli/go/cmd/ontos at v0.14.0, and is reproduced verbatim:

The --from-json notation is the only text→bytes path in the tool, and it exists for authoring and debugging only. The discipline is explicit in the spec: never sign, hash, or exchange the JSON text — hash the emitted bytes. And hash the octets, not their hex spelling: piped straight into sha256sum, canon --emit's output would hash its 21 bytes of hex text and newline instead of the ten octets. A pleasant text form was deliberately not invented, because a pleasant notation risks becoming a second, exchangeable value surface.

§04

Eight registered readings — and not one new equality

ontos/data · L2 · byte forms frozen

L2 is where the world gets expressed, and it is deliberately opinionated about exactly one thing: representation. Each label fixes the single canonical spelling of a datum. None of them defines equality — that stays L0's, structural, inherited unchanged.

The v1 label set — four scalars, three structural kinds, one no-value
labelshapethe canonical rule
int Tuple(Atom("int"), Atom(payload)) Exact and unbounded in principle. Payload is one sign byte (00 non-negative, 01 negative) then the big-endian magnitude with leading zeros stripped. Zero is exactly the single byte 00; there is no negative zero.
utf8-text Tuple(Atom("utf8-text"), Atom(utf8)) Valid UTF-8, verbatim — no Unicode normalization, no NFC, no NFD. Two canonically-equivalent but byte-distinct strings are distinct values. A consumer wanting normalization defines a separate later embedding.
bool Tuple(Atom("bool"), Atom(marker)) A single payload byte: 00 false, 01 true. Exactly two well-formed values; any other payload is not a bool.
decimal Tuple(Atom("decimal"), int(m), int(e)) Exact m × 10e, never IEEE-754. Zero is decimal(int 0, int 0); a non-zero mantissa carries no trailing base-10 zero. So 3.14 is uniquely decimal(int 314, int −2). Not a general rational — 1/3 has no decimal form.
list Tuple(Atom("list"), e₀ … eₙ₋₁) Order and multiplicity are identity: [a,b] ≠ [b,a] and [a] ≠ [a,a]. Never sorted, never deduplicated. The bare unlabeled tuple is forbidden — without the label it is indistinguishable from a compound, which is exactly what let blind encoders fork list identity.
map Tuple(Atom("map"), Tuple(k,v) …) Entries are arity-2 pairs, sorted strictly ascending by key under the codec's total order. Strictness gives canonical order and key-uniqueness in one check.
set Tuple(Atom("set"), e₀ … eₙ₋₁) Elements sorted strictly ascending under the same total order — canonical order and no-duplicates, again in one check.
null Tuple(Atom("null")) Exactly one inhabitant, forever. No undefined, no nil, no missing, no typed-null. It means present-but-no-value, which is not absence — absence stays structural, an omitted key.

L2 constrains producers, not just readers

The three producer-admission laws are the part most encoders get wrong. Concretely for utf8-text: a host string carrying an unpaired surrogate is outside the domain and MUST be rejected. It must not be encoded verbatim — that mints a value the reader rule makes unreadable. And it must not be "repaired" by substituting U+FFFD, because that succeeds with a different datum, and the substitution is undetectable once the host string is gone.

Two things that are not divergence. First, host integer types differ by language — Go takes *big.Int, TypeScript takes bigint — both unbounded, matching the unbounded byte form. Second, map and set are the only codec-version-relative embeddings, because their canonical order comes from the codec; the other six are purely structural.

§06

The tool: bytes in, evidence out

ontos CLI · built from source · not published

ontos answers one question — what are these bytes, are they canonical, and what do they read as? Its seam is an invocation contract, not a function signature, and both of its output formats are byte-pinned across implementations. Even --format human must be byte-identical in all four: implementations disagreeing on a line a human reads is exactly the favored-language wart the project forbids.

The four commands — all four ship in every implementation

ontos decode [<hex>]decode the bytes to the L0 value treethe value, or a rejection code

A recognition miss is not an error. There is no not_recognized code. read --kind int on a non-integer returns a positive-shaped result — {"ok":true,…,"recognized":false} — and exits 1. The boolean field carries the answer; the exit code makes it scriptable.

Recognition is structural, not materialization. A canonical int whose magnitude exceeds a binding's host integer width is still recognized: true in every binding. Host width is a separate concern, and never a recognition miss — which is what lets the implementations agree byte-for-byte on such values.

§07

How four implementations are stopped from disagreeing

vectors · differential harness · CI

The claim "no favored language" is not a policy statement; it is a check that fails. The differential harness drives every implementation over a shared corpus and compares them byte-for-byte on stdout and on the exit code — an implementation that emits the right bytes with the wrong exit code fails. A fifth implementation in any language can prove conformance by being registered as one more --impl, with no in-process test code ported at all.

Three check modes, one corpus
  • decode — hex in, JSON Lines out. The default.
  • author→bytes (--from-json-roundtrip) — inverts the protocol, driving canon --emit --from-json over each vector's authoring value.
  • human (--human-roundtrip) — the same corpus at --format human, asserting the human rendering is byte-identical too.

Run locally with scripts/check.sh conformance, which rebuilds every CLI first so a stale binary cannot manufacture a false divergence. scripts/check.sh fuzz adds the generative differential bout across all four CLIs.

Re-run for this sheet over the Go and Python implementations, in all three modes: 44 byte strings × 5 commands, the same 44 at --format human, and 44 author→bytes cases, all byte-identical, every emitted hex equal to the pinned one.

It is a claim about evidence, not about effort.

§08

What ontos refuses to do

non-goals — load-bearing, not modesty

Each of these is a deliberate exclusion with a reason and an owner elsewhere. They are the most useful thing on this sheet for deciding whether ontos is what you need: if you are looking for one of them, you are looking for a different repo.

  • No truth, inference, or proof. ontos does not know what follows from what. Variables, rules and proof belong to a logic engine above it — logos.
  • No authority, identity, or attestation. It does not know who said a thing or whether it counts. Facts, signers and trust belong to an authority layer — arche signs over the bytes.
  • No persistence, location, addressing, or time. It does not know where a value lives or when. References and content addresses belong to a storage layer.
  • No schema, validation, or interpretation. It does not say what a thing means — only that it is, and of what kind.
  • No arithmetic. Numeric equality, arithmetic and ordering belong to the reasoner and the domain. A domain that wants 2/4 = 1/2 normalizes at the producer; ontos never adds the equation.
  • No third constructor, and no variable. The tag set is closed; the codec cannot encode a variable. A consumer needing one must define its own codec and must not redefine 0x00 or 0x01.
  • No ordering at L0. The total order is codec-derived, explicitly not part of identity.
  • No floating point, ever. It would break one-canonical-form-per-value. decimal is exact and is not a general rational.
  • No Unicode normalization. Keeping it out keeps v1 self-contained and avoids baking one normalization regime into the floor.
  • No second no-value. Explicitly against the prior art: CBOR shipped both null and undefined and DAG-CBOR had to ban one to regain canonicity; Ion's typed nulls multiply the no-value across every type.

And one refusal about itself: the codec is not the model. It is a side axis that answers one question — what are the canonical bytes of a value — and adds no values and no identity. A value is the abstract tree; the bytes are the one spelling everyone agrees to write it in.

Where to go next

the normative surface is the specs

The specifications under docs/spec/ are the source of truth: when code and specification disagree, the specification is right until a pull request changes it. The implementations conform to the specs, not the other way round.

If you came to use it

Install from §05 — public registries, no credential, one release number in every lane. Reach for encode / decode, and take every hash and signature over the octets they produce, never over a text form or its hex spelling. In Rust, keep one ontos per dependency graph.
