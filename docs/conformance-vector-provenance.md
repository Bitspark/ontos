# Conformance-vector provenance (Class A oracle vs Class B derived)

**Status:** policy (normative for how vectors are *authored*, not for the byte
contract itself). Resolves the tension between the hand-authored-oracle rule and
the codec-dependent `map`/`set` byte forms (issues ontos-internal#22/#23/#24).

The conformance vectors under [`vectors/`](../vectors/) are the cross-language
contract: an implementation conforms iff it agrees with them on every judgment
([`vectors/README.md`](../vectors/README.md)). For that to mean anything, the
vectors must be an **independent oracle**, not a mirror of one implementation.
[`vectors/README.md`](../vectors/README.md) states the rule plainly:

> Author it by hand against the spec and compute bytes by hand; do **not** paste
> an implementation's output back in as the expected value (that would make the
> vector test the implementation against itself).

That rule is exactly right for scalars, `bool`, text, and small `list`s. It is
**not** mechanically achievable for `map` and `set`, whose canonical **entry /
element order** is the `ontos-codec-v1` byte order over the key/element
([ontos-codec §6](spec/ontos-codec.md), [ontos-data §5.7–§5.8](spec/ontos-data.md)).
Hand-computing that sort order over heterogeneous keys is impractical and
error-prone — so historically those byte-forms were produced by the real encoder,
which quietly violated the "never paste an implementation's output" rule.

The resolution is **not** to pretend generated bytes were hand-authored, and
**not** to weaken the oracle. It is to **split authorship from derivation** and
make the distinction explicit and reviewable.

## The principle

> **The oracle is the human-authored source plus the specified derivation rule;
> the committed generated bytes are a reviewed artifact, not the oracle itself.**

A vector author is responsible for the *intent* (which value, which membership)
and for the *rule* that turns intent into bytes (the spec's canonicalization).
For Class A the author also computes the bytes; for Class B the bytes are
**derived** from the author's intent by that rule, by a deliberately boring
generator, and then **cross-checked** against all four encoders (the three
production encoders plus the `py` validation lane).

## Two classes of vector

Every conformance vector is exactly one of two provenance classes, recorded in a
`provenance` field on the authoring source.

### Class A — independent hand-authored oracle (`"provenance": "hand-authored"`)

For the cases whose bytes a human can compute by eye: the codec vectors
([`vectors/codec.json`](../vectors/codec.json)), the L0 identity vectors
([`vectors/identity.json`](../vectors/identity.json)), and the scalar / `bool` /
`utf8-text` / `list` / `decimal` embeddings in
[`vectors/data.json`](../vectors/data.json). `decimal` (§5.9) is Class A despite
nesting `int` children: it is codec-independent (canonical form is purely structural),
so its hex is the `decimal` tuple wrapper composed over the already-pinned `int` child
encodings — mechanical to compute and check by eye.

Requirements:

- The **value** is authored by hand against the spec.
- The **hex** is authored or checked **independently from the spec**, by hand —
  never pasted from any `go`/`rs`/`ts` implementation's output. (`encode(Atom(b))
  = 00 ‖ uvarint(len) ‖ b`, `encode(Tuple(v*)) = 01 ‖ uvarint(arity) ‖ encode(child)*`
  — short enough to compute and check by eye.)
- Cases are kept small enough to verify by eye.

These remain the **strongest** oracle set and stay directly in
[`vectors/data.json`](../vectors/data.json) / `codec.json` / `identity.json`. They
do **not** flow through the generator. (`data.json` does not currently carry an
explicit `provenance` field on each Class A case; the class is documented here and
the `data.json` `note` records that the int/text/bool/list/decimal hex are
hand-authored canonical payloads. The codec runner replays them unchanged.)

### Class B — derived canonical-order (`"provenance": "derived-from-spec-algorithm"`)

For `map` and `set`, whose canonical order is **defined by `encode(value)` byte
order** and is therefore impractical to hand-compute.

The human authors the **unsorted semantic case**, not the final byte string:

- The **membership** — a `map`'s `entries` (`[key, value]` pairs) or a `set`'s
  `elements` — written in a **deliberately non-canonical order** (we use the
  *reverse* of the canonical order, so the file visibly is not already sorted).
- An **`order_explanation`**: a short note stating *why* the canonical order is
  what it is, **by codec bytes** (e.g. "a bare atom, tag `00`, sorts before any
  embedding, tag `01`; between two embeddings the label-length uvarint `03 < 09`
  decides"). This is the human's auditable claim about the derivation.

A generator then **derives** the `value` and `hex`:

1. Parse the source authoring notation into an `ontos/core` `Value`.
2. Build the canonical `Value` with `@bitspark/ontos-data`'s `encodeMap` /
   `encodeSet`, passing the **non-canonical** entries/elements — the encoder is
   what **sorts** by the `ontos-codec-v1` byte order and rejects duplicates.
3. `encode` that `Value` with `@bitspark/ontos-codec` → the canonical `hex`.

The derived `{ value, hex }` are written to a **clearly-marked, committed
artifact** ([`vectors/data.generated.json`](../vectors/data.generated.json)) — a
reviewed artifact, **not** the oracle. The oracle is
[`vectors/data.source.json`](../vectors/data.source.json) (the membership +
`order_explanation`) plus the derivation rule above.

## File layout

```text
vectors/data.source.json      # Class B SOURCE — human-authored map/set membership
                              #   (reverse order) + order_explanation. The oracle.
vectors/data.generated.json   # Class B DERIVED — committed, clearly-marked artifact;
                              #   { name, value, hex } produced by the generator.
vectors/data.json             # The pinned canonical vectors the cross-language tests
                              #   replay (Class A directly + the map/set bytes).
tools/vector/gen.mjs          # ontos-vector — the maintainer generator + reproduce-check.
```

`vectors/data.json` stays the file the `go`/`rs`/`ts` runners replay, and it is
**not** edited by this reform: the generator must **reproduce** its `map`/`set`
cases, never change them.

## Why a generated artifact is still oracle-grade: the cross-check

A generator that is "the encoder with a JSON loop" would only grade the encoder
against itself. Two things prevent that:

1. **The generator is deliberately boring and reviewable** — a tiny recursive
   authoring-notation ↔ `Value` mapper plus the three steps above, no fancy deps
   beyond the `@bitspark/ontos-*` packages. Its logic is auditable against the
   spec, and the `order_explanation` in the source states the expected order
   independently.
2. **The reproduce-check IS the differential cross-check.** After deriving, the
   generator **asserts** that every derived `{ value, hex }` reproduces the
   corresponding `map`/`set` case in `vectors/data.json` **byte-for-byte**, and
   **exits non-zero on any mismatch**. `vectors/data.json` is already pinned
   byte-for-byte to **all four** encoders — the three production encoders
   (`go`/`rs`/`ts`) plus the `py` validation lane — by the codec vector-runner;
   reproducing it therefore cross-checks the derived bytes against four
   independent implementations, not just one. If a case fails to
   reproduce, the fix is to the **source or the generator** — **never** to
   `data.json`.

This mirrors how deterministic-encoding systems are tested in practice: the
source of truth is the canonicalization *rule*, and test artifacts may be
generated from that rule, provided provenance, a derivation trace, review, and
differential checking are all present.

## The `provenance` field and the derivation trace

- `provenance` takes exactly one of two values:
  - `"hand-authored"` — Class A (value and hex authored/checked from the spec by
    hand, never pasted from an implementation).
  - `"derived-from-spec-algorithm"` — Class B (value and hex derived from the
    human-authored membership by the specified rule).
- **Derivation-trace requirement (Class B).** Every Class B source case MUST carry
  an **`order_explanation`** justifying the canonical order by codec bytes, and the
  derived artifact MUST record its derivation provenance: the `provenance`, the
  `source` file, the `generator` path, the `profile`, and the `codec` id (see the
  `note`/header fields in
  [`vectors/data.generated.json`](../vectors/data.generated.json)). Together the
  source `order_explanation` and the generated header are the auditable trace from
  intent → derived bytes. The generator's own reproduce-check output (how many
  cases reproduced `data.json`) is the runtime evidence that the trace holds.

## Codec-version relativity

`map`/`set` order is `ontos-codec-v1`'s `order`. A future `ontos-codec-v2` would
change the order, hence the canonical `map`/`set` bytes — a **new** `map`/`set`
version, regenerated against v2, never an in-place edit (mirrors the codec freeze:
the byte mapping changes only by version, [ontos-codec §7](spec/ontos-codec.md)).
The Class B source (`data.source.json`) is codec-version-independent (it is just
membership + an explanation); the derived artifact is relative to the codec the
generator links.

## How to regenerate / verify

From the repo root, after building `core` + `codec` + `data`:

```sh
node tools/vector/gen.mjs
```

It rewrites `vectors/data.generated.json` and asserts every `map`/`set` case
reproduces `vectors/data.json` byte-for-byte, exiting non-zero on any drift. See
[`tools/vector/README.md`](../tools/vector/README.md).
