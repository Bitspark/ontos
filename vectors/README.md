# ontos conformance vectors

Language-agnostic vectors that **every** ontos implementation (`go`, `rs`, `ts`)
replays. They are the contract: an implementation conforms iff it agrees with the
vectors on every judgment. This is what turns cross-language agreement from a hope
into a checkable property — and it is the prerequisite that lets a new language
(e.g. Go) be added safely: it conforms iff it passes these.

Most of these vectors are **hand-authored from the specs**, not generated by any
implementation — so they are an independent oracle, not a mirror of one codec. The
exception is the structural `map`/`set` cases in `data.json`, whose canonical
entry/element order *is* the `ontos-codec-v1` byte order and so is impractical to
hand-compute: those are **Class B** (derived) — generated by `tools/vector/gen.mjs`
from a human-authored, codec-independent source and cross-checked against all four
encoders. The split is **Class A** (hand-authored independent oracle: `identity.json`,
`codec.json`, and the scalar/`bool`/`utf8-text`/`list` cases of `data.json`) vs
**Class B** (derived `map`/`set`), per
[`docs/conformance-vector-provenance.md`](../docs/conformance-vector-provenance.md).

## How a value is written in a vector

Vectors describe abstract ontos values in a small JSON form. **This JSON is a
vector-authoring notation only — it is NOT ontos's canonical encoding** (that is
`ontos/codec`, and it is bytes, not JSON).

```text
Atom(bytes)        →  { "atom":  "<lowercase-hex>" }     // "" means the empty atom
Tuple(v0, v1, …)   →  { "tuple": [ <value>, … ] }        // [] means the empty tuple
```

Hex strings have even length; `""` is the empty byte string. Every value is
exactly one of these two object shapes (mirrors `Value = Atom | Tuple`).

Examples:

```json
{ "atom": "" }                              Atom("")            the empty atom
{ "atom": "61" }                            Atom(0x61)
{ "tuple": [] }                             Tuple()             the empty tuple
{ "tuple": [ { "atom": "61" } ] }           Tuple(Atom(0x61))
```

## Files

### `identity.json` — L0 structural identity *(pins `ontos/core`, the frozen floor)*

```text
{ "cases": [ { "name", "left": <value>, "right": <value>, "equal": <bool> }, … ] }
```

A conforming `core` implementation MUST report `equal(left, right) == equal` for
every case. Covers: atom equality by exact bytes (incl. length:
`Atom(0x01) ≠ Atom(0x0001)`), `Atom("") ≠ Tuple()`, tuple order / arity / nesting
distinctions, and atom/tuple disjointness. Pure model — no bytes, no codec.

### `codec.json` — the byte codec *(pins `ontos/codec`, frozen `ontos-codec-v1`)*

```text
{
  "codec":   "ontos-codec-v1",
  "uvarint": [ { "n": <int>, "hex": "<bytes>" }, … ],
  "encode":  [ { "name", "value": <value>, "hex": "<bytes>" }, … ],
  "reject":  [ { "name", "hex": "<bytes>", "code": "<reason>" }, … ]
}
```

- **uvarint** — `encodeUvarint(n)` MUST equal `hex` (shortest LEB128).
- **encode** — a conforming codec MUST satisfy *both* directions:
  `encode(value) == hex` (canonical/deterministic) **and** `decode(hex) == value`
  (round-trip). The `hex` is the one canonical encoding of `value`.
- **reject** — `decode(hex)` MUST fail with the given stable `code`:
  `unexpected_eof`, `trailing_bytes`, `unknown_tag`, `non_canonical_uvarint`,
  `uvarint_overflow`. (Codes are normative; an implementation's human-readable
  message is not.)

`codec.json` pins the frozen codec `ontos-codec-v1` (`docs/spec/ontos-codec.md`).

### `codec-limits.json` — operational limit reporting *(pins `ontos-codec.md` §4.2, **not** the byte contract)*

```text
{
  "codec": "ontos-codec-v1",
  "cases": [ { "name", "hex": "<bytes>",
               "limits": { "maxDepth"?, "maxAtomBytes"?, "maxTupleArity"? },
               "expect": "accept" | { "code": "limit_exceeded", "limitKind": "<kind>" } }, … ]
}
```

- Each face decodes `hex` under `limits` with its **library** API and MUST either
  accept, or reject with `limit_exceeded` and the given **limit kind** (`decode_depth`,
  `atom_bytes`, `tuple_arity`). A bound absent from `limits` keeps the face's shipped
  default (depth 1024; atom bytes and tuple arity unbounded), so `{}` is the default
  policy, and the two `default_depth_*` cases pin that default as exact.
- Every case is built so that exactly one bound can stop it. Where two bounds could
  fire, the kind a face reports is observational (§4.2) and is deliberately not pinned.
  `native_width` is target-specific (TS at 2^53, Go and Rust on 32-bit builds), so it is
  tested in each face's own suite rather than here.
- This file is kept apart from `codec.json` on purpose. `codec.json` is the frozen byte
  corpus; this one is policy, which the CLIs never read and whose output they do not
  change (ontos-internal#352, research 0003 row 14).

### `data.json` — `ontos/data` (L2) embeddings *(pins `ontos-data-v1`)*

```text
{
  "profile": "ontos-data-v1",
  "codec":   "ontos-codec-v1",
  "encode":  [ { "name", "datum", "value": <L0 value>, "hex": "<bytes>" }, … ]
}
```

Each `encode` case pins one `ontos/data` embedding (`int` / `utf8-text` / `bool` /
`list` / `map` / `set`, per `docs/spec/ontos-data.md`) by giving its **L0 value**
and the **full `ontos-codec-v1` encoding** of that value. The same encode-vector
contract as `codec.json` applies (`encode(value) == hex` **and** `decode(hex) ==
value`), so the existing codec runner replays it — this is what pins the
embeddings' canonical payload bytes across `go`/`rs`/`ts`/`py`. The structural
`map` and `set` cases are **Class B** (derived) vectors — their entry/element
order is `ontos-codec-v1` byte order, generated by `tools/vector/gen.mjs` and
cross-checked against all four encoders (see
[`docs/conformance-vector-provenance.md`](../docs/conformance-vector-provenance.md)).

### `data-json.json` — `ontos-data-json/1` projection lock *(pins the PAIR `(ontos-data-json/1, ontos-codec-v1)`)*

A **cross-repo derivation lock**, distinct from the files above in both purpose and
shape. It pins the `ontos-data-json/1` profile (`docs/spec/ontos-data-json.md`): the
named projection from domain JSON into `ontos/data`, then `ontos-codec-v1` bytes,
then SHA-256 — plus the domain-separated era-2 preimage `Tuple(Atom(tag), value)`
that identity-bearing consumers (e.g. the `lab`/`foundry` bind2/decl2 digests) sign
over. It carries lab tally's cross-repo vector convention **verbatim**, not the
house `{encode, reject}` shape:

```text
{
  "profile": "ontos-data-json/1",  "codec": "ontos-codec-v1",  "schema", "note",
  "corpus":  { "path", "sha256" },                      // the deep byte corpus, pinned
  "valid":   [ { "desc", "value": { "doc"|"docSource",
                 "expect": { "codecSha256", "era2": { "tag", "digest": "sha256:…" } } } }, … ],
  "reject":  [ { "desc", "value": { "docSource",
                 "expect": { "reject": { "path", "reason" } } } }, … ],
  "duplicateKeys": { "note",                            // the opt-in strict mode (ontos-internal#322)
    "reject": [ { "desc", "value": { "docSource",
                  "expect": { "reject": { "path", "key" }, "lastWinsEquivalent" } } }, … ],
    "accept": [ { "desc", "value": { "docSource" } }, … ] }
}
```

- **duplicateKeys** — the opt-in `duplicateKeys: reject` source-admission mode
  (ontos-internal#322; spec §*The projection*, *The opt-in strict mode*). Hand-authored,
  digest-free: each `reject` case must be refused by the strict mode at `path`
  naming `key` (the first repeat, as decoded), while the default mode projects it
  to the same bytes as the hand-written `lastWinsEquivalent`; each `accept` case
  is duplicate-free and must project byte-identically in both modes. Every
  `valid`/`reject` case above also holds unchanged under the strict mode.
- **valid** — each case pins one domain document's projection: the inner digest
  (`codecSha256`) and the era-2 wrapped digest (`era2.digest`). `doc` is a live JSON
  value (lossless for pure int/string/bool/object/array); `docSource` is raw JSON
  source text, used where a number literal's exact lexical form must survive (a
  parsed JSON number cannot distinguish `1e3` from `1000.0`). `preprocess` /
  `corpusKey` name any pre-projection step (e.g. the decl2 `description` strip) and
  the corresponding key in the deep corpus.
- **reject** — each case pins a **path-named refusal**: the JSON `path` and stable
  `reason` for a form `/1` does not graduate (the reserved decimal arm — fraction /
  exponent literals).

Unlike Class A, these expectations **are** harness-derived — but from the *frozen*
`data`+`codec` libraries whose own bytes are independently pinned by `codec.json` /
`data.json` above, and cross-checked through the shipped `ontos canon --emit` CLI, so
this file does not test an implementation against itself at the codec layer. The deep
byte corpus (full projected value trees + full hex, per document) lives in the
sibling **`data-json.oracle.json`**, pinned here by `corpus.sha256` so it is
reachable and drift-evident without the ~155 KB blob crossing repos. Enforcement of
these derivation cases currently rides **lab's gate** (the bidirectional lock);
the existing per-language vector runners load their own fixed files and are inert to
this one. Add-only revision discipline (`ontos-data-json/2` may only assign a reading
to a form `/1` rejects, never re-point an accepted arm) makes every digest here
drift-proof by construction.

## Adding a case

Author it by hand against the spec and compute bytes by hand; do **not** paste an
implementation's output back in as the expected value (that would make the vector
test the implementation against itself). Keep cases small enough to verify by eye.
For the derived `data-json.json` lock, re-run the profile oracle rather than editing
digests by hand, and re-pin `corpus.sha256` in the same change.
