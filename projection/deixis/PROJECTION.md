# ontos over deixis — the projection profile

**Profile:** `ontos-over-deixis-v1`. **Status:** additive. **Maturity: UNWITNESSED, permanently** — three implementations (Rust, `projection/deixis/rs`; Go, `projection/deixis/go`; TypeScript, `projection/deixis/ts`, browser-compatible, ontos-internal#323), **all ontos-authored**. The vectors here are **hand-authored from this profile, not generated by an implementation** (see §Vectors and the file's own `note`) — so they are better evidence than implementation-produced goldens would be, and the Go face replayed all 17 UNADJUSTED on its first run, written from this document alone by an author who had not read the Rust. That is two independent readings of `P`/`R` agreeing on every outcome. The TypeScript face is **not a third reading**: it was written with both existing faces open, as a consumer implementation for a browser inspector, and it changes nothing below — a third ontos-authored face does not move the maturity line (ontos-internal#255), and was never claimed to. What the two readings still cannot show is that an implementer **outside ontos** would reach the same reading — which is the property four-language parity supplies for `core`/`codec`/`data` ([`ontos-conformance.md` §Maturity](../../docs/spec/ontos-conformance.md#maturity--what-a-surfaces-conformance-actually-rests-on), ontos-internal#191). **That property will not be acquired here: the aspiration is closed, not pending** (ontos-internal#255). The witness seal — an implementation of `P`/`R` written from this document alone, by an author who has read neither face nor `vectors/ontos-projection.json` — is one-shot and cannot be restored once spent. It went unspent **not for want of an eligible witness**: one was found, answered the seal with an evidential inventory rather than a recollection, and was ruled seal-intact at the **cross-organisation, code-sealed** tier — the strong form this profile could have claimed. The choice was therefore a real one, and it was put in those terms: spend the one intact seal on the board, or accept that this profile stays `unwitnessed`. The operator accepted `unwitnessed`. The seal is also **perishable** — its holder works the deixis side of this bridge and may read the corpus incidentally at any time — so it is not being held in reserve for a later attempt; the aspiration is closed. That is this profile's ceiling by decision, not a gap awaiting work. Note the other projection, `ontos-data-json/1`, is also unwitnessed and also multi-face (go · rs · ts) — so the two now overlap in all three languages rather than sitting in disjoint ones. Neither witnesses the other regardless, because every face of both is ontos-authored. Nothing in `ontos/core`,
`ontos-codec-v1`, existing vectors, or any downstream hash changes; this directory is the
one place in ontos that knows [deixis](https://github.com/Bitspark/deixis) exists, and the
dependency direction is `ontos → deixis` — the bridge imports `deixis-core` and
`deixis-pos`, never the reverse.

deixis records *that* ontos is the densely-position-keyed subset of a deixis tree
(its `docs/ONTOS.md`). This profile makes the correspondence executable, and it owns
everything ontos-specific about it: the projection `P`, the recognizer `R`, their laws,
and the conformance vectors. What it builds on from deixis is generic and carries no
ontos knowledge: the tree, its identity, and the position spelling
**`deixis-pos-v1`** (`κ : ℕ → Bytes` — injective, prefix-free, order-preserving; see
deixis `docs/design/0002-positional-keys.md`).

## The codomain: `Node[Option[Bytes]]`

deixis `v0.2.0` makes a node's own value **mandatory and independent of its children** —
`Node[T] = T x FinMap[Bytes, Node[T]]`, so there is no longer a `Leaf | Struct` sum to
case on. Every node has both halves.

That leaves this profile to say what the payload *is*, and the choice is
**`Option[Bytes]`**. **`Option` is this bridge's payload domain, not a feature of the
deixis core.** The core carries `T` opaquely, never interprets it, and takes no position
on optionality; deixis ships `Option` as an opt-in payload type precisely so a profile
like this one can pick it. The reading is ours: `Some(b)` is *an atom's bytes*, `None` is
*no atom here — a tuple's positions instead*.

The two ontos constructors therefore land on two **disjoint node shapes**:

| ontos | payload | children |
| --- | --- | --- |
| `Atom(b)` | `Some(b)` | none |
| `Tuple(v0 … vn-1)` | `None` | exactly `κ(0) … κ(n−1)` |

and the shapes that are *neither* are exactly what `R` refuses. Note what this buys law 6
for free: the empty atom and the empty tuple are **both childless**, and they differ in
the payload alone.

## The projection and the recognizer

`P : Ontos → Node[Option[Bytes]]`, **total**:

```text
P(Atom(b))            = Node(Some(b), {})
P(Tuple(v₀ … vₙ₋₁))   = Node(None, { κ(i) ↦ P(vᵢ) | 0 ≤ i < n })
```

`R : Node[Option[Bytes]] ⇀ Ontos`, **partial**:

```text
R(Node(Some(b), m))  = Atom(b)                              defined only when m = {}
R(Node(None, m))     = Tuple(R(m(κ(0))), …, R(m(κ(n−1))))   where n = |dom m|,
                       defined only when dom m = { κ(0), …, κ(n−1) }
                       and every child recognizes.
```

`R` reads the payload first, because that is what decides which kind of node it is
looking at. `m = {}` in the first clause is not a formality: a node carrying **both** a
payload and children is well-formed deixis and outside the image of `P`, and it is a
shape the old `Leaf | Struct` sum could not even express.

Because `κ` is order-preserving, deixis's canonical entry order *is* tuple order: the
recognizer walks entries once, comparing each key against the generated `κ(i)` — it never
parses a key, and needs no `κ` decoder.

**What `R` must never do:** sort entries into new positions, fill gaps, drop keys, or
normalize an alternate spelling of an index to its position. `Node(None, {κ(0), κ(2)})`
fails. A key that would *decode* to 1 but is not octet-equal to `κ(1)` fails. And it must
not **strip** either half of a node to make it fit: dropping a stray payload to read the
children as a tuple, or dropping children to read the payload as an atom, are repairs of
exactly the same kind. Recognition is exact or it is refusal — anything looser is a repair
pass, and a repair pass silently coarsens identity, which no layer may do.

## The laws

`=O` is ontos structural identity. `=D` is deixis identity **lifted from this profile's
slot relation**, which the bridge must supply and does:

```text
Some(b) =payload Some(c)   iff  b = c   octet for octet
None    =payload None
None    ≠payload Some(b)                for every b, including b = ""
```

deixis deliberately provides no native equality for a node — it lifts one from the slot
and declines to choose the slot's relation on a caller's behalf. So `=D` here is that
lift over the **whole** `Option[Bytes]` payload, and both halves are load-bearing:
collapsing `None` into `Some("")` would merge the empty tuple with the empty atom, which
is law 6.

1. `R(P(v)) = v` — projection loses nothing.
2. `R(d)` succeeds iff `d` is in the image of `P` — recognition is exact.
3. `R(d) = v` implies `P(v) =D d` — recognition inverts onto the same node.
4. `P(v) =D P(w)` iff `v =O w` — the projection is an embedding of identities.
5. `d =D e` implies the same recognizer outcome, and equal outputs on success.
6. `Node(Some(""), {}) ≠D Node(None, {})` — empty atom and empty tuple stay distinct;
   the case a lax bridge would merge first. In the mandatory-value model both are
   **childless**, so this law rests entirely on the payload relation above.
7. The ontos index path `(i₀, …, iₖ)` reaches a subvalue iff the deixis key path
   `(κ(i₀), …, κ(iₖ))` reaches its projection — pointing commutes with `P`.

## Bytes

The only byte-level statement this profile makes is compositional, through `R` and the
frozen codec:

```text
toOntosBytes(P(v)) = encodeOntosV1(v)    byte for byte
```

There is deliberately no law relating any deixis codec's bytes to `ontos-codec-v1`: a
deixis codec must encode keys, this codec elides them, and the two encode different
structures by design. The conformance tests replay `vectors/codec.json`'s frozen bytes
through `P`/`R` to pin the equation above.

## Vectors

[`vectors/ontos-projection.json`](vectors/ontos-projection.json) is hand-authored from
this profile. ontos values use the family's vector notation (`{"atom": hex}`,
`{"tuple": […]}`); deixis nodes use the parallel form:

```text
Node(own, m)  →  { "own": "<lowercase-hex>" | null,
                   "children": [ ["<lowercase-hex-key>", <node>], … ] }
```

`own` is the whole payload: a hex string is `Some(bytes)` — including `""` for
`Some("")` — and `null` is `None`. Every node carries both fields, so there is no
constructor to choose between.

Children are an array of pairs **in authored order** — a JSON object would
canonicalize away entry-order independence, which is one of the things the vectors
exercise (`entries_authored_out_of_order`). `project` cases pin `P` and, read backwards,
`R` (laws 1–3); `unrecognized` cases pin refusal; `d_distinct_nodes` pin the payload
relation in the direction `d_equal_nodes` cannot reach.

**The `reason` field is INFORMATIVE, not normative.** What conformance requires of an
`unrecognized` case is that `R` **refuses** it — the outcome, not the wording. The reasons
are authored commentary on why each case is interesting, and a conforming implementation
is free to report the refusal however it likes.

This is stated because the opposite reading is unimplementable, and a second implementer
found it by hitting it (ontos-internal#253 → ontos-internal#255). Several reasons here describe a
classification the recognizer is **forbidden to compute**:

| the reason says | what it would require |
| --- | --- |
| the key `61` *spells no position* | classifying a key as non-positional |
| `ff000001` *would decode to 1 under a lax reader* | decoding the key |
| a dense prefix plus a *named straggler* | classifying the straggler |

…while `R` above "walks entries once, comparing each key against the generated `κ(i)` — it
never parses a key, and needs no `κ` decoder". To an implementation that obeys that, all
three are one condition: **entry `i`'s key is not octet-equal to `κ(i)`**. Requiring the
wording would therefore force a second implementer either to fail conformance or to copy
the first implementation's text — and copying is precisely what spends the independence a
second witness exists to provide. The laws (1–7) mention reasons nowhere, which is the
other half of the argument: they fix outcome classes and are silent on diagnostics, the
same posture `ontos-data.md` §4.1 takes for producer admission.

⇒ A conforming face asserts the refusal and **may report reason divergence, never match
it**. `projection/deixis/go` does exactly that, deliberately.

### …but the `kind` IS normative, and that is not a retreat from the above

Each `unrecognized` case also carries a **`kind`**, one of:

| `kind` | the node | what is wrong |
| --- | --- | --- |
| `key_mismatch` | `Node(None, m)` | `dom m` is not `{ κ(0) … κ(n−1) }` |
| `value_with_children` | `Node(Some(b), m)`, `m` non-empty | a payload beside children — not a tuple at all |

**Why this can be required when the wording cannot.** The argument above is that the
reasons demand a classification `R` is *forbidden to compute* — deciding that a key
"spells no position" means decoding it. `kind` demands nothing of the sort. Every
conforming `R` **already** branches on the payload before it looks at a single key,
because that is what tells an atom from a tuple; `kind` is just which branch refused.
It is free, it needs no `κ` decoder, and two independent implementers reading the
definitions above cannot disagree about it.

**Why it is worth requiring.** The mandatory-value model admits a shape the old sum could
not express, and a face that funnelled it into the key explanation would report a key as
the culprit when every key is a flawless `κ` — see the `value_with_dense_children` and
`value_with_malformed_children` cases, whose whole point is that the domain is not the
problem. A refusal that names the wrong defect is worse than a terse one.

The shape question is decided **first**: a node with a payload and children is refused as
`value_with_children` even when its keys are also malformed, because it was never a tuple
and its domain was never required to be positional.
